## 1. 项目定位与技术结构

### 1.1 项目定位

项目定位为一个集 **AI 五子棋对弈、棋力评估、残局训练、随机连珠、好友实时对战、积分成长与个性化棋盘皮肤** 于一体的浏览器端应用。

项目的核心目标不只是实现五子棋规则，而是形成完整的竞技闭环：

- **对弈：** 提供不同难度的 AI 对手，以及好友实时 PVP。
- **评估：** 记录棋谱、思考时间、关键攻防与落子质量，形成棋力反馈。
- **训练：** 通过多步残局和不同连珠规则训练战术能力。
- **成长：** 通过积分、排行榜、Elo 和荣誉头衔体现长期进步。
- **体验：** 通过棋盘/棋子皮肤、全局主题、音效和动画提高产品完成度。

### 1.2 当前技术结构

| 层级 | 当前技术/职责 |
|---|---|
| 前端 | HTML、CSS、JavaScript；各版本使用独立目录与独立 Pages 入口 |
| 静态部署 | GitHub Pages，保留历史版本入口 |
| 身份认证 | Supabase Auth，负责邮箱注册、验证、登录与 Token |
| 云端 API | Cloudflare Workers，负责账号相关业务、棋谱校验、积分结算及 PVP 服务 |
| 数据存储 | Cloudflare D1，保存账号关联数据、挑战记录、积分账本和对局信息 |
| 实时对战 | Cloudflare Durable Objects / Worker 实时服务，负责房间状态与双方同步 |
| 本地体验 | AI 落子、计时、棋谱等尽量在浏览器本地执行，终局再与服务端同步 |
| 质量保障 | Node 语法检查、自动化测试、D1 迁移测试、GitHub Actions 部署与健康检查 |

### 1.3 版本隔离原则

- 每个重要版本保留独立目录和在线入口，例如 `/v3.4/`、`/v4.0/`。
- 新版本不直接覆盖已验证的旧版本。
- 数据库结构变更必须通过版本化 migration 管理，禁止只改线上表结构而不留迁移记录。
- 前端页面部署成功不代表 Worker、D1 和真实对局链路全部验收成功。

## 3. 各版本更新档案

### 3.1 V1：初始版本

- 项目最早期的五子棋页面，作为后续版本的基础。
- 当前仓库保留 `/v1/` 历史入口。
- 现有 README 未提供 V1 的完整功能变更记录，因此本档案不对未留档的早期功能作推测。

### 3.2 V2.1：棋力评估与复盘

**核心目标：** 从基础对弈升级为能够解释玩家落子质量的棋力评估工具。

主要能力：

- 新手、进阶、大师三档 AI 对弈。
- 逐手棋谱、单手思考时间、复盘跳转与候选落点建议。
- 棋力评估包含 Top-1 / Top-3、估计落子损失、严重失误率、复杂度加权准确度、关键攻防成功率及样本可信度。
- 对局结束后冻结计时，并禁止继续悔棋。
- 本地积分、皮肤商店、棋谱 JSON 导出。

**评分口径（V2.1 文档记录）：**

设：
- (Q)：复杂度加权的平均落子准确度（0–100）。
- (T)：存在明确可处理攻防机会时的成功率（百分制）。
- (E)：可评分着法中的严重失误率（百分制）。

存在战术机会时：

`Score = 0.75 × Q + 0.15 × T + 0.10 × (100 − E)`

不存在战术机会时：

`Score = 0.90 × Q + 0.10 × (100 − E)`

Top-1 / Top-3 用于展示，不直接加分；对局长短不直接增加或扣除分数，样本量用于估计可信度。

**重要限制：** 该评分依赖有限层数的候选着法搜索，不等同于专业棋力等级、Elo 或真实胜率；提示位置也不是经过校准的获胜概率。

### 3.3 V2.2：账号、积分与商店系统

**核心目标：** 建立账号体系、云端数据和可持续的积分成长系统。

主要更新：

1. **棋盘与棋子皮肤**
   - 购买前可预览棋盘配色。
   - 棋盘皮肤与棋子皮肤独立选择、自由组合。
2. **悔棋经济**
   - 每局前 3 次悔棋免费。
   - 第 4 次起每次消耗 10 积分。
   - 对局结束后禁止悔棋。
3. **落子提示**
   - 点击提示后才显示候选位置，最多展示 Top-3。
   - 落子、新开局、悔棋或离开对弈页后清除提示。
4. **开始与计时**
   - 新开局默认显示 `00:00`。
   - 点击“开始下棋”后才允许落子并启动总计时和单手思考计时。
5. **账号系统**
   - 邮箱注册、登录、邮箱确认、找回密码、自定义显示名称。
   - 管理员支持用户查询、积分调整、封禁及审计日志。
   - 管理员不能封禁或重置自己的账号。
6. **积分与排行榜**
   - 新手、进阶、大师 AI 胜局奖励分别为 10、30、80 分。
   - 综合排名积分与可消费余额分离，购买皮肤或悔棋不直接扣除竞技排名分。
   - 排行榜独立展示原始胜率，并根据修正胜率进行排名修正。
7. **娱乐化反馈**
   - 增加本局小结，对胜负、落子表现和关键机会进行文字反馈。

**云端结构：** Supabase Auth + Cloudflare Workers + Cloudflare D1。

**数据边界：** 游客积分保存在本地浏览器，不应视为正式云端成绩。

### 3.4 V2.3：本地优先、低延迟与猫猫主题

**核心目标：** 解决在线架构逐手请求造成的落子延迟，同时强化视觉体验。

主要更新：

- AI 落子、计时和棋谱在浏览器本地执行，不再每一步等待 Worker 往返。
- 开局后台创建云端会话；对局结束后再提交棋谱与事件流。
- Worker 对玩家落子、AI 应手、胜负及悔棋费用进行服务端验证。
- 终局数据可写入本地待同步队列；登录、网络恢复或手动重试时重新提交。
- 通过 D1 的结算状态与幂等逻辑，避免重复提交导致重复结算。
- 新增猫咪咖啡馆棋盘、猫爪装饰、猫猫棋子和可开关的 Web Audio 落子音效。
- 建立 6 种棋盘主题与 6 种棋子主题；棋盘主题控制页面整体氛围，棋子主题控制强调色和交互光效。

**猫猫棋子显示问题的最终处理：** 曾尝试使用透明 WebP 图片绘制棋子，但用户截图反馈棋盘只显示最后一步红色标记、黑白棋子不可见。随后补充图片加载/缓存保护，并进一步修复为不依赖图片透明像素的 Canvas 直接绘制路径，增加回归测试，避免图片解码或 Alpha 通道导致整盘棋子消失。

### 3.5 V3.0：好友真人 PVP

**核心目标：** 从单人 AI 对弈扩展到好友在线竞技。

主要能力：

- 通过邀请码创建和加入房间。
- 双方准备后开始实时对局。
- 实时同步落子与对局状态。
- 10 分钟棋钟。
- 认输、和棋与断线重连。
- 真人 Elo 排行榜和历史战绩。
- 服务端校验落子、时钟与胜负。
- 真人 Elo 与 AI 积分分开统计，不改变 AI 积分体系。

**验收记录：** 用户曾明确反馈 V2.3、V3.0 测试通过且稳定；V3.0 是后续版本的真人 PVP 基础。

### 3.6 V3.1：对弈页面 UI 优化

- “开始下棋”按钮只在 AI 对弈页面显示。
- AI 棋盘与 AI 操作区只在“对弈”和“复盘”页面显示。
- 商店、排行榜、账号管理等非对弈页面不再展示无关棋盘。
- 好友 PVP 棋盘独立，不受 AI 棋盘显隐规则影响。
- 继承 V3.0 的主题、账号、AI 与棋力评估能力。

### 3.7 V3.2：残局挑战与随机连珠初版

**新增模式：**

- **残局模式：** 自动生成不同难度的挑战，通关奖励为 10 / 30 / 80 积分；登录用户通过服务端生成、保存和验证挑战，游客奖励保存在本地。
- **随机连珠模式：** 每局随机选择 3–10 连珠规则，棋盘尺寸满足 `size >= 2 × connect + 3`，采用空盘开局以避免随机障碍造成死局。
- **奖励保护：** D1 保存挑战记录，登录用户一次性领取奖励，并设置每日生成/领取限制。

**用户实测反馈与后续调整：**

- 初版残局过于简单，存在一步制胜，缺乏真正的多步推演。
- 初版随机模式 AI 未充分根据目标连珠数调整搜索，玩家容易连续获胜。
- 用户明确要求残局改为多步且唯一解，并要求随机 AI 根据连珠数调整策略。

上述反馈成为 V3.3 / V3.4 强化的直接依据。

### 3.8 V3.3：王者 AI 与战术模式强化

- 最高难度由“大师”调整为“王者”，保留原 `hard` 配置键和 80 分胜局奖励。
- 王者 AI 搜索从深度 2 / 候选宽度 7 提升至深度 3 / 候选宽度 9。
- 为根节点候选分配独立节点预算，降低搜索顺序偏差。
- 优先检查直接获胜点和必须防守点，并处理多重即时威胁。
- 随机连珠 AI 按 3–10 连珠目标调整搜索深度、候选宽度、回应宽度和节点预算。
- 残局改为多步组合：唯一正确起手制造双路威胁，对手封堵一路后，玩家沿另一路完成制胜。
- 对残局进行程序验证：初始局面无一步制胜点、正确起手唯一、双路威胁成立、封堵与终结落点合法。

**限制：** 王者 AI 仍是启发式搜索，不是数学证明的完美求解器；残局的唯一性验证针对指定战术结构和正确首着，不应宣传为整棵博弈树只有一条完整棋谱。

### 3.9 V3.4：深层搜索与积分结算修复

- 开局时锁定难度快照，保证前端选择的难度、云端会话记录和最终奖励一致。
- 修复王者难度被错误记录为进阶、导致奖励错发的问题；王者胜利按 80 分结算。
- 王者 AI 引入迭代加深 Alpha-Beta 搜索、Zobrist 置换表、着法排序和强制防守延伸。
- 默认搜索预算约 2.4 秒。
- 随机连珠 AI 改为时间受限的迭代加深搜索。
- AI 搜索移入 Web Worker，降低思考过程对页面交互的阻塞。

**限制：** 搜索增强代表实战能力提升，不代表数学意义上的必胜。仍需通过固定测试局面、自我对弈和用户实战验证。

### 3.10 V4.0：视觉与竞技系统升级

**视觉体验：**

- 采用暖象牙白、樱花粉和木质棋盘的整体视觉方案。
- 统一导航、卡片、统计区域与交互控件。
- 桌面端采用双栏布局，移动端采用单栏自适应布局。
- 保留账号、云端积分、皮肤商店、猫猫棋子、复盘、残局和随机连珠模式。

**AI 对弈：**

- 玩家可选择执黑先手或执白后手。
- AI 搜索、落子提示、悔棋、复盘、棋谱校验和云端结算均适配实际玩家颜色。
- AI 平局触发幸运猫猫动画。
- 平局奖励为对应难度胜局基础奖励的 5 倍：新手 50、进阶 150、王者 400。
- 平局奖励仅适用于标准 AI 对弈；随机连珠模式没有独立积分奖励。

**真人 PVP：**

- 双方准备完成后，由 Worker 使用 Web Crypto 生成骰子点数。
- 同点自动重掷，胜者获得黑棋先手。
- 骰子结果由服务端生成、写入 D1 并同步双方，前端负责动画展示。
- 真人 PVP 和棋仍按独立 Elo 规则处理，不参与 AI 平局积分奖励。

**排行榜：**

- AI 积分榜与真人 Elo 榜前三分别展示“棋圣、棋王、棋宗”头衔及领奖台。

**维护修复：**

- 修复旧版 D1 残局表结构缺少 `solution_moves` 等字段导致的残局生成失败。
- 增加 `0007_repair_mode_challenges.sql`，修复迁移历史与实际表结构不一致的问题，并保留已有挑战记录、奖励和领取状态。
- 修复管理员用户中心在 Token 刷新后偶发隐藏的问题。
- 皮肤收藏卡片跟随当前棋盘主题色，解决深色棋盘下固定浅色卡片突兀的问题，并提升名称文字对比度。
- 修复执白玩家的棋力评分错误统计黑棋的问题，实时评分、复盘和棋谱 JSON 导出统一按玩家实际执棋颜色统计。

- 验证平局重复提交不会重复入账，真人 PVP 和棋不会触发 AI 平局奖励。
- 验证残局生成、完整多步解题、服务端验证、一次性领取奖励和每日限制。

### 阶段二：V4.1 AI 棋力与残局质量提升

任务：

- 建立固定开局、战术局面和残局测试集，覆盖直接成五、冲四、活三、双威胁、必防点和多重威胁。
- 建立 V3.4 与 V4.x AI 的同局面回归，统计胜率、和棋率、失误率、平均思考时间和节点消耗。

- 为搜索设置时间上限和节点上限，监控移动端性能，避免极端局面造成长时间卡顿。
- 根据实际通关率、平均解题时间和提示使用率校准残局难度。
- 继续保持服务端对残局答案和奖励领取的校验，避免客户端伪造通关。

建议指标：

| 维度 | 建议指标 |
|---|---|

### 阶段三：V4.2 竞技与成长体验

目标：让单局游戏形成长期可持续的竞技体验。

可选任务，需先根据用户反馈确定优先级：

- 真人 Elo 分段与赛季排行榜。
- 每日残局挑战和连续挑战记录。
- 个人棋力曲线，区分 AI 评分、真人 Elo 和训练表现。
- 对局历史筛选、关键局面收藏与棋谱分享。
- 复盘中标记关键失误、错失胜机和最佳防守点。
- 对局成就、赛季荣誉和合理的反作弊机制。

设计原则：

- AI 积分、消费余额和真人 Elo 必须保持清晰隔离。

- 任何新增奖励必须由服务端验证，不以客户端显示作为入账依据。

### 阶段四：V5.0 架构与产品升级（中长期）

目标：在功能规模扩大后，降低版本维护成本并提高可扩展性。

建议方向：

- 抽离统一的棋盘规则、胜负判断、AI 搜索、评分、棋谱和主题模块，减少多个版本之间复制代码造成的维护分叉。
- 将 AI 引擎与 UI 解耦，使普通对弈、随机连珠和残局模式复用同一套可配置引擎。
- 建立统一的对局事件模型，兼容本地对弈、云端结算和实时 PVP。
- 建立版本化 API 与数据库 schema 管理规范。
- 建立自动化浏览器测试、性能回归和发布前健康检查。
- 对重要算法变更保留基准数据，避免仅凭主观体验判断 AI 是否变强。

## 7. 版本发布与质量控制规范

每个正式版本建议固定经过以下流程：

1. **需求冻结：** 明确版本目标、功能边界和验收标准。
2. **分支开发：** 使用独立 feature/fix 分支，避免直接在主分支试验。
3. **代码检查：** 运行语法检查、单元测试和关键业务回归测试。
4. **数据库验证：** 对所有 migration 执行旧表结构、全量迁移和历史数据保留测试。
5. **备份：** 涉及 D1 schema 变更或数据迁移时，部署前先备份。
6. **后端优先：** 先部署 Worker 和 migration，确认健康检查通过，再发布依赖新 API 的前端。
7. **前端发布：** 发布到独立版本目录，保留旧版本入口。
8. **自动化验收：** 检查 GitHub Actions、Pages、Worker 和 API health。
9. **人工验收：** 按真实账号、真实浏览器、移动端和断网场景执行测试。
10. **文档归档：** 同步 README、版本变更记录、Bug 修复记录和验收结果。

### 7.1 每个 PR 的最低要求

- 写明用户问题、修改方案、影响范围和回滚方式。
- 明确是否改变积分规则、棋力评分、棋盘规则或数据库结构。
- 新增 Bug 必须增加回归测试，避免修复后再次出现。
- 涉及服务端奖励时必须验证幂等、身份校验和重复请求。
- 不得把“CI 通过”描述为“真实用户场景全部通过”。

### 7.2 版本状态用语

| 状态 | 使用条件 |
|---|---|
| 开发中 | 功能仍在分支开发，未合并 |
| 已合并 | PR 已进入主分支 |

**通道 A：Self-Play 强化学习**

- 同一个 TEBA-Net-S 分别执黑和执白，与自身对弈。
- PUCT 访问次数分布作为 Policy 监督。
- 最终胜负作为 Value 标签。
- 规则分析器生成 WIN_NOW / MUST_BLOCK / FORK 辅助标签。

**通道 B：Champion Sparring 强化学习**

- TEBA-Net-S 与实际 V4.0 王者 AI 对弈。
- 对手直接调用 `v4.0/src/engine.js`，不重新实现近似算法。
- 旧版王者 AI 使用迭代加深 Alpha-Beta、置换表、战术排序和战术延伸。
- 每局交换 TEBA 黑棋/白棋身份，控制先手偏差。
- TEBA 自己的落子使用 PUCT 策略目标和最终胜负进行训练。

**低权重冠军策略蒸馏**

- 仅保留旧版王者 AI 获胜或和棋的对局中的王者落子作为低权重 Policy 示范。
- 王者 AI 输掉的整局轨迹不被当成专家策略。
- 示范数据只参与 Policy Loss，不直接参与 Value / Tactical Loss。

训练目标为：

`L = 0.6 L_self-play + 0.4 L_champion-sparring + 0.15 L_teacher-policy`

其中前两项分别使用 Policy + Value + 0.2 × Tactical 多任务目标，最后一项仅为低权重策略模仿损失。两个强化学习通道在每轮联合更新；数据生成按通道顺序执行，避免 M4 上并行搜索争用资源。

### 9.8 论文实验边界

1. Self-Play only。
2. Champion Sparring RL only。
3. Self-Play + Champion Sparring，不使用策略蒸馏。
